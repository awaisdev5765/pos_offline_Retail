Offline POS System - App Summary
================================

Project Overview
----------------
This project is a Flutter offline-first POS application focused on retail workflows, with local SQLite storage (Drift), Riverpod state management, and go_router navigation. The app is designed to run without internet, and includes optional LAN-based multi-PC data sync using TCP sockets.

Core Architecture
-----------------
- Frontend + app logic: Flutter (Dart)
- Local database: SQLite via Drift
- State management: Riverpod
- Routing: go_router
- Localization: easy_localization (English/French/Arabic)
- Desktop support: window manager + system tray behavior
- Optional data sync: LAN discovery and TCP socket sync
- Backup systems: local backup, Windows auto-backup, optional cloud upload helper

10) Banking and Financial Tracking

13) Printing and Receipt Output

Key End-to-End Flows
--------------------
Flow A: App Start -> Access Gate
1. App launches and initializes localization/services.
2. Splash screen checks license status.
3. If invalid: route to license activation.
4. If valid: continue to setup/login decision.

Flow B: First-Time Setup
1. Detect setup not complete.
2. Open business setup form.
3. Save business profile + admin credentials.
4. Mark setup complete.
5. Navigate to login.

Flow C: Secondary Device Bootstrap (Multi-PC)
1. Start discovery for admin host in LAN.
2. If admin found, connect sync service.
3. Pull/sync required setup data.
4. Move to login once ready.

Flow D: Login -> Main App
1. User enters admin/employee credentials.
2. Local auth validation runs.
3. On success, user enters shell navigation and dashboard/POS modules.

Flow E: POS Sale Completion
1. Cashier builds cart and selects payment method.
2. Credit rules and limits are validated (if credit sale).
3. Sale + sale items are saved to local DB.
4. Stock quantities are reduced per sold items.
5. Customer due values update when relevant.

Flow F: Purchase/Restock
1. User creates purchase invoice/order.
2. Purchase record saves and triggers related refresh/update logic.
3. Inventory reflects incoming stock flow.

Flow G: Customer/Supplier Payment
1. Open customer or supplier payment screen.
2. Record payment against ledger/account.
3. Balances and related report views update.

Flow H: Return/Refund
1. Locate sale/transaction.
2. Create return/refund entry with line items.
3. Inventory and financial records reconcile accordingly.

Flow I: Backup Lifecycle
1. User or scheduler triggers backup service.
2. Database file copied/versioned in backup location.
3. Optional restore path available when needed.

Flow J: Sync Lifecycle (LAN)
1. Admin service listens for clients.
2. Client connects and exchanges sync messages.
3. Database table updates propagate across nodes.

Tech Stack Snapshot
-------------------

- Drift ORM + SQLite local DB
- Riverpod providers/notifiers
- go_router navigation
- Easy localization

- SharedPreferences-based local configuration

Operational Notes
-----------------
- Project is offline-first and does not rely on an always-on backend in this repo.
- Documentation/schema suggest multi-business-mode intent, but active runtime paths appear retail-centric in places.
- Automated tests are minimal; core reliability currently depends more on runtime flows than broad test coverage.
